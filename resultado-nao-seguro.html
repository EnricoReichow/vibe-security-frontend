Crítica

Credencial de API exposta no código

src/config/payments.js:14

Encontramos uma senha de acesso (uma "chave de API") escrita diretamente dentro do código, junto com as configurações de pagamento. É como deixar a senha do cofre anotada numa etiqueta colada nele: qualquer pessoa que veja esse código consegue usar essa chave para acessar sua conta de pagamentos.

Uma chave de API da Stripe (sk_live_••••••••1a2b) está hardcoded em texto plano no arquivo src/config/payments.js:14 e foi versionada no histórico do Git. Qualquer pessoa com acesso ao repositório (ou a um fork público, se houver) pode extrair a chave e realizar operações na conta da Stripe associada.

O que fazer

  1. Não compartilhe esse repositório publicamente até corrigir isso.
  2. Peça para quem administra a conta de pagamentos (Stripe) revogar essa chave imediatamente e gerar uma nova.
  3. Peça a um desenvolvedor para mover essa chave para fora do código, num "cofre de variáveis de ambiente", ele vai entender esse termo.
Remova a chave de API da Stripe hardcoded em src/config/payments.js e substitua por uma leitura da variável de ambiente STRIPE_SECRET_KEY (via process.env). Adicione um arquivo .env.example com a variável vazia, garanta que .env está no .gitignore, e não deixe nenhum valor sensível hardcoded no código.

Dependência desatualizada com falha conhecida

package.json · lodash@4.17.15

Uma das ferramentas prontas ("bibliotecas") que o projeto usa por baixo dos panos está desatualizada e tem uma falha de segurança já conhecida publicamente. É como usar uma fechadura com um defeito que já foi divulgado. Quem souber do defeito pode tentar se aproveitar dele.

A dependência lodash está na versão 4.17.15, vulnerável a um caso de "prototype pollution" (CVE-2020-8203) que pode permitir a manipulação de objetos internos da aplicação e, em certos fluxos, levar a negação de serviço. Corrigido a partir da versão 4.17.19.

O que fazer

  1. Peça para um desenvolvedor atualizar a biblioteca "lodash" para a versão mais recente.
  2. Depois de atualizar, rode os testes do projeto (ou peça para alguém rodar) para garantir que nada quebrou.
  3. Repita esse processo periodicamente: dependências desatualizadas são uma das causas mais comuns de invasões.
Atualize a dependência lodash no package.json para a versão ^4.17.21 (ou mais recente), reinstale as dependências e verifique se não há quebras de compatibilidade nos pontos do código que usam funções do lodash.

Ausência de validação de entrada

src/routes/pedidos.js:42 · POST /api/pedidos

A rota que recebe novos pedidos aceita qualquer informação enviada, sem checar se ela faz sentido antes de usar. É como aceitar qualquer envelope pela porta sem olhar o que tem dentro. Alguém pode aproveitar isso para enviar algo malicioso em vez de um pedido de verdade.

O endpoint POST /api/pedidos consome o corpo da requisição diretamente, sem validação de schema ou sanitização de tipos/tamanhos. Isso abre espaço para payloads malformados, uso indevido de campos não esperados e ataques de injeção em camadas posteriores.

O que fazer

  1. Peça a um desenvolvedor para adicionar uma validação dos dados recebidos antes de processá-los.
  2. Garanta que campos obrigatórios sejam checados e que tipos incorretos sejam rejeitados com uma mensagem clara.
Adicione validação de schema (ex.: com zod ou joi) no corpo da requisição do endpoint POST /api/pedidos em src/routes/pedidos.js, rejeitando com status 400 qualquer payload que não corresponda ao formato esperado (campos obrigatórios, tipos e tamanhos).

Baixa

Cabeçalhos de segurança ausentes

configuração global do servidor

O site não está enviando algumas instruções extras de segurança para o navegador de quem acessa. Sozinho isso não é grave, mas é uma camada de proteção a mais que está faltando.

A aplicação não define cabeçalhos HTTP de segurança recomendados (Content-Security-Policy, X-Content-Type-Options, Strict-Transport-Security). Isso reduz as camadas de defesa contra XSS, sniffing de MIME e downgrade de conexão.

O que fazer

  1. Peça a um desenvolvedor para adicionar uma biblioteca de segurança padrão (como o "helmet", se o projeto usa Node.js), que já configura essas proteções automaticamente.
Adicione o middleware helmet ao servidor Express deste projeto para configurar automaticamente os cabeçalhos de segurança recomendados (Content-Security-Policy, X-Content-Type-Options, Strict-Transport-Security, entre outros).
